### Confirmed diagnostic limitation: Prisma's reported database name is misleading

Latest provided auth failures occur at `prisma.user.findUnique()` with `PrismaClientInitializationError: User was denied access on the database 127.0.0.1`.

The exact Prisma engine revision from the log (`c2990dca591cba766e3b7ef5d9e8a84796e47ab7`) maps PostgreSQL SQLSTATE 28000 to DatabaseAccessDenied by extracting the sixth whitespace-separated token. For the earlier raw psql `no pg_hba.conf entry for host "127.0.0.1", user ..., database ...` error, this token is the client IP. Locally reproducing that parser returns `127.0.0.1`, not the actual database name. SQLSTATE 28P01 separately maps to AuthenticationFailed.

Therefore the current error does not prove DATABASE_URL still uses localhost or that the password is wrong. It is consistent with host-based authentication denial. Current raw PostgreSQL SQLSTATE/message and the effective Node connection tuple remain unobserved.

## 2. Deployment automation — failures verified in actual CI output

Audited run: https://github.com/Bagasbzz/kelkam/actions/runs/36321443207

1. **Migration runs on the wrong machine for a loopback DB URL.** `.github/workflows/deploy.yml:10,28-49` runs Prisma on GitHub-hosted Ubuntu. The log at 13:10:27Z reports P1001 for `127.0.0.200:5432`. Loopback is local to the runner, not JKC. Seed also failed. SQL recovery repairs the current schema, not this CI design.
2. **Uploaded ZIP was not installed by this run.** Lines 160-229 call speculative Fileman extraction functions. All five returned missing-function/status 0; extraction was skipped. Uploading an archive does not activate its build. Exact currently served BUILD_ID is not verified.
3. **Automated restart failed.** Lines 231-247 call Fileman/save_file; response was HTTP 200 but JSON status 0 with missing function. No response-status validation fails the job. This says nothing about subsequent manual cPanel restarts.
4. **Automatic .env and .htaccess writes failed.** Lines 249-320 use the same missing function, and continue despite failure. This disproves the earlier assumption that GitHub Secrets were successfully propagated by this run. HTTP 200 alone is not cPanel operation success.
5. **False-green deployment status.** Migration/seed/extraction/env/restart failures do not reliably fail the job. Lines 322-328 check only GET `/`; homepage returned 200 while DB-dependent routes failed. Even homepage failure is only a warning.
6. **Restart precedes .env writing.** Independently of the missing API, the step ordering can start a process with old config before the new env is written. There is no second restart after env write.

A repaired pipeline needs a supported deployment method, explicit JSON status validation, release/build identity verification, env installation before restart, database execution from an accessible environment, and a DB/schema/auth readiness test. Do not trigger another unchanged deployment as a purported fix.

## 3. Startup and routing inconsistency

- `server.js:56-69` is a custom server stripping `/keluhkampus.my.id` from the internally rewritten pathname.
- `public/.htaccess:17-20` rewrites root requests into that prefix and documents the dependency on the custom server.
- `scripts/build-deploy.js:65-70` copies standalone output and then overwrites its server.js with the custom root file.
- CI `.github/workflows/deploy.yml:69` instead keeps Next's generated standalone server. Local generated output was inspected: it sets `__NEXT_PRIVATE_STANDALONE_CONFIG`, calls `startServer`, and has no custom prefix adapter.
- Thus the two packaging paths have different routing/startup behavior. Whether JKC strips the prefix itself in the current environment still requires runtime verification; blindly extracting/replacing server.js can introduce a routing regression.
- Next's warning about `next start` can be emitted by the custom `next()` server path too (`node_modules/next/dist/server/next.js:225-227`). It is not proof cPanel invokes the npm `start` command.
- The missing webpack file is consistent with custom startup against a minimal standalone dependency tree: `next/dist/server/config.js:1154-1162` tries a webpack hook and rethrows absent standalone configuration. Old log evidence is not proof that this is today's failing auth step.

## 6. Authentication and account lifecycle

These code findings are independently confirmed and must not be confused with the observed failure at the initial user.findUnique connection step.

1. **Same-second session ID collision.** `src/lib/server/auth.ts:136-145` signs only sub/email/role/iat/exp with deterministic HS256. There is no unique jti. Two requests for the same user in the same second produce the same token; this was reproduced with the installed jose library and dummy inputs. `auth.ts:184-185` inserts that token as the session primary key. Two otherwise successful same-second logins can therefore produce a unique-constraint error/500 on the second insert. This does not explain today's initialization denial. Add per-session randomness before relying on retries/concurrent logins.
2. **Registration can persist an account while returning failure.** `src/app/api/auth/register/route.ts:78-84` creates the user and then creates the session outside a shared DB transaction. If session insertion fails, the account remains; a repeat registration then returns 409. Make the database writes atomic and handle response-cookie errors explicitly. No evidence this failure mode has happened to this user's account.
3. **Admin seed only promotes existing accounts.** `prisma/seed.ts:21-28` uses updateMany, not create/upsert. Zero matching rows is logged without failure; CI's actual seed invocation also failed to connect. Schema installation does not create hensellbagas@gmail.com or grant it ADMIN. Check account existence and promote only the intended account after registration is verified.
4. **Missing JWT secret is not rejected in production.** `src/lib/server/auth.ts:60-62` and `src/proxy.ts:94-96` retain a known development fallback. This is unsafe configuration handling, not evidence of a deployed missing secret or a complete account-takeover path (DB session checks also exist). Production should fail clearly when the secret is absent. Earlier screenshots demonstrate a value was entered, not the effective serving-process value.
5. **Anonymous /api/auth/me 401 is expected with this proxy.** It is protected in `src/proxy.ts:62`; absent-cookie handling returns 401. AuthProvider handles no user. It neither establishes nor disproves successful DB connectivity.
